# 1 기본 형식

- 문서는 UTF-8(8-bit Unicode Transformation Format) Markdown으로 저장.
- `AGENTS.md`를 포함한 관리, 지식, 리소스 설명, 프로토타입 설명, 로그 문서는 파일 최상단에 YAML(YAML Ain't Markup Language) 프론트매터 배치.
- 문서 제목은 프론트매터의 `title`에서 관리. 1단계 헤더(H1, Heading 1)는 본문의 대분류로 사용. Article의 첫 `문서 정보` H1은 관리 정보 표시용 예외이며 [Article 문서 정보의 번호 예외](#33-article-문서-정보의-번호-예외) 준수.
- 아래 본문 항목은 기본 구성. 문서 목적에 맞게 항목명과 상세 수준 조정 가능.
- 예시의 `문서 제목`, `문서명`, `작성일` 등은 실제 값으로 대체. 확인된 출처가 없는 경우 `sources: []` 유지와 사유의 본문 기록.

# 2 문서 제목과 파일명

- `title`은 문서 제목, 파일명은 파일 저장과 식별을 위한 이름. 서로 별개의 항목이며 `title` 수정 시에도 파일명은 자동으로 변경되지 않음.
- 일반 지식 문서, 리소스 설명 문서와 프로토타입 설명 문서는 기본적으로 파일명의 확장자를 제외한 이름과 `title` 일치. 예: `전투 시스템.md`의 `title`은 `전투 시스템`.
- 고정 이름을 사용하는 운영 문서와 월별 로그는 예외. 예: `AGENTS.md`의 `title`은 `위키 작업 지침`, `2026-10.md`의 `title`은 `2026년 10월 작업 로그`.
- 기존 운영 문서의 파일명 유지. 파일명 변경 시 해당 파일을 가리키는 링크도 함께 갱신.
- 문서 제목의 본문 H1 중복 표기 없이 첫 대분류부터 본문 시작.

# 3 헤더 넘버링

## 3.1 번호 형식

| 레벨 | 번호 형식 | Markdown 예시 |
|---|---|---|
| H1 | `1`, `2`, `3` | `# 1 대분류` |
| H2(Heading 2) | `1.1`, `1.2`, `1.3` | `## 1.1 중분류` |
| H3(Heading 3) | `1.1.1`, `1.1.2`, `1.1.3` | `### 1.1.1 소분류` |
| H4(Heading 4) | `1)`, `2)`, `3)` | `#### 1) 세부 항목` |
| H5(Heading 5) | `(1)`, `(2)`, `(3)` | `##### (1) 상세 항목` |

- 번호와 헤더 제목 사이에 공백 하나 배치.
- H1 번호 끝에는 마침표를 붙이지 않음. 예: `# 1 개요`.
- 헤더 레벨의 건너뜀 없이 정보 계층에 맞게 사용.
- 헤더 번호와 본문의 번호 목록은 서로 독립적으로 관리.

## 3.2 번호 초기화와 갱신

### 3.2.1 레벨별 번호 부여

- 번호 적용 대상 H1은 문서 본문 순서대로 `1`부터 연속 부여. Article의 첫 문서 정보 절은 [번호 예외](#33-article-문서-정보의-번호-예외)에 따라 제외.
- H2는 H1 번호에 해당 H1 안의 순번 추가. H1 변경 시 마지막 순번은 `1`부터 재시작.
- H3는 H2 번호에 해당 H2 안의 순번 추가. H2 변경 시 마지막 순번은 `1`부터 재시작.
- H4는 각 H3 안에서 `1)`부터, H5는 각 H4 안에서 `(1)`부터 재시작.

### 3.2.2 절 변경과 참조

- 절 추가, 삭제, 이동 시 해당 문서의 번호 갱신. 변경된 헤더를 가리키는 링크도 점검.
- 특정 절 참조 시 문서명과 헤더 제목 병기. 세부 참조 방식은 [문서 작성 규칙: 근거와 판단의 표시](문서%20작성%20규칙.md#5-근거와-판단의-표시) 준수.
- 변경 이력 표의 과거 절 번호는 당시 기록으로 보존. 현재 절 번호로 일괄 치환 금지.

## 3.3 Article 문서 정보의 번호 예외

- 적용 대상: `type: article`인 `03_Articles` 하위 문서와 `target_folder: 03_Articles`인 `90_Workspace` 하위 Article 초안.
- 문서 정보가 있는 경우 첫 H1을 `# 문서 정보`로 표기. `0`을 포함한 번호 생략.
- 문서 정보 절의 하위 헤더도 번호 생략. 다음 H1 직전까지 번호 계산에서 제외하며 헤더 계층과 링크 검사는 유지.
- 첫 본문 H1부터 `1`로 시작. H2 이하에는 기존 번호 형식 적용.
- 문서 정보가 없는 경우 첫 본문 H1부터 `1`로 시작. 형식 통일을 위한 빈 문서 정보 절 추가 불필요.

# 4 프론트매터

| 필드 | 적용 | 값과 의미 |
|---|---|---|
| `title` | 공통 필수 | 문서 제목 문자열 |
| `type` | 공통 필수 | `system`, `reference`, `synthesis`, `article`, `asset`, `prototype`, `log` 중 하나 |
| `created` | 공통 필수 | 최초 작성일. `"YYYY-MM-DD"` 문자열 |
| `updated` | 공통 필수 | 마지막 내용 수정일. `"YYYY-MM-DD"` 문자열 |
| `status` | 지식, 리소스 설명, 프로토타입 설명 문서 필수 | `draft`, `review`, `confirmed`, `superseded`, `rejected` 중 하나 |
| `sources` | 지식, 리소스 설명, 프로토타입 설명 문서 필수 | 실제 사용한 근거 문서와 원자료 목록 |
| `source_check` | References 필수 | `unverified`, `partial`, `verified`, `not_applicable` 중 하나 |
| `reviewed` | 확정 Article, Asset, Prototype 필수 | 마지막 검토일. `"YYYY-MM-DD"` 문자열 |
| `review_note` | 확정 Article, Asset, Prototype 필수 | 실제 수행한 검토와 남은 한계의 간단한 기록 |
| `target_folder` | Workspace의 지식, 리소스 설명, 프로토타입 설명 문서 필수 | 최종 목적 폴더. `01_References`, `02_Syntheses`, `03_Articles`, `04_Assets`, `05_Prototypes` 중 하나 |
| `asset_files` | 리소스 설명 문서 필수 | 해당 설명 문서가 관리하는 리소스 경로 목록 |

## 4.1 출처 기록

- `sources`의 내부 문서 링크는 위키 루트 기준 Obsidian 링크 문자열로 기록. 예: `"[[01_References/문서명]]"`.
- 외부 원자료는 URL 또는 식별 가능한 서지 정보 기록. 페이지, 절, 시점 등 세부 근거 위치는 본문에 기록.
- `sources`에 운영 규정이나 작업 로그 포함 금지. `target_folder`의 허용 범위는 루트의 [위키 작업 지침: 허용 입력 출처](../../AGENTS.md#42-허용-입력-출처) 준수.

## 4.2 상태와 대조 범위

- `status`는 문서의 작업과 채택 상태. `confirmed`는 모든 출처 내용의 사실 입증을 의미하지 않음.
- `source_check`는 원자료 대조 상태. `verified`도 원자료 자체의 완전한 진실성을 보증하지 않음. 확인 방법과 범위는 본문에 기록.
- 원자료 미대조 시 `unverified`, 일부 대조 시 `partial`, 해당 범위 대조 완료 시 `verified`로 기록. 외부 사실 검증 대상이 아닌 사용자 요구사항 등은 사유와 함께 `not_applicable`로 기록 가능.
- `superseded`는 다른 내용으로 대체된 문서, `rejected`는 채택하지 않은 작업물. 현재 확정 내용과의 혼합 방지를 위해 대체 위치나 사유를 본문에 표시.

# 5 References

```yaml
---
title: "문서 제목"
type: reference
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
status: draft
sources: []
source_check: unverified
---
```

- 기본 본문: `자료 개요` → `출처와 작성 방식` → `내용` → `확인 범위와 미확인 사항`.
- 출처와 작성 방식에 외부 자료, 사용자 작성, 대규모 언어 모델(LLM, Large Language Model) 작성 등의 경위 명시.
- LLM 작성 설명은 그 자체로 외부 사실의 입증 자료가 될 수 없음. 근거가 있는 내용은 원자료 연결, 나머지는 미확인으로 표시.

# 6 Syntheses

```yaml
---
title: "문서 제목"
type: synthesis
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
status: draft
sources:
  - "[[01_References/문서명]]"
---
```

- 기본 본문: `목적과 범위` → `종합, 비교, 분석` → `해석과 추론` → `한계와 추가 확인 사항`.
- 분석에 사용한 자료와 주장별 근거 위치 기록.

# 7 Articles

```yaml
---
title: "문서 제목"
type: article
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
status: draft
sources:
  - "[[01_References/문서명]]"
  - "[[02_Syntheses/문서명]]"
---
```

- 기본 본문: `목적과 범위` → `본문` → `한계와 미정 사항` → `근거`.
- 변경 이력 등 문서 정보가 있는 경우 본문 앞에 배치하고 [Article 문서 정보의 번호 예외](#33-article-문서-정보의-번호-예외) 적용.
- 문서 정보의 버전 번호는 사용자가 결정. Codex는 사용자가 명시한 버전 값만 반영하고 임의 부여나 증가 금지. 버전 변경 이력 행은 사용자의 명시적 지시에 따라 반영. Codex의 작업 기록은 월별 로그에 작성.
- 실제 사용한 출처만 유지. 기존 확정 Article 사용 시 해당 링크도 기록.
- 확정 시 `reviewed`와 `review_note` 추가. 이후 내용 수정 시 검토 기록도 갱신.

# 8 Assets

## 8.1 적용 대상과 프론트매터

- 이미지, 영상, 음원 파일은 프론트매터 적용이 불가능하므로 Markdown 설명 문서 함께 배치. 예: `장면.png`와 `장면.md`.
- 리소스 설명 문서와 실제 리소스 함께 관리.

```yaml
---
title: "리소스 제목"
type: asset
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
status: draft
sources: []
asset_files:
  - "04_Assets/파일명.png"
---
```

## 8.2 본문과 검토 기록

- 기본 본문: `용도` → `파일과 규격` → `입력 자료와 생성 또는 편집 방법` → `검토 결과와 한계`.
- 생성 시 실제 사용한 프롬프트나 설정이 있는 경우 재현에 필요한 범위에서 기록.
- `asset_files`는 위키 루트 기준 경로로 기록. Workspace 작업 중에는 현재 경로 기록, 확정 반영 시 갱신.
- 확정 시 `reviewed`와 `review_note` 추가.

# 9 Prototypes

## 9.1 적용 대상과 기본 구성

- 프로토타입별 하위 폴더에 프로젝트 파일과 설명용 Markdown 문서 함께 관리.
- YAML 프론트매터는 프로젝트 설명용 Markdown 문서에만 적용. 소스 코드와 실행 파일에는 삽입하지 않음.
- 설명 문서의 파일명과 `title`은 [문서 형식: 문서 제목과 파일명](#2-문서-제목과-파일명)의 일치 원칙 준수.
- 기본 본문: `목적` → `입력 근거` → `실행 방법` → `검토 결과` → `한계`.
- 실행 방법에 필요한 환경, 의존성과 실행 명령 기록.

## 9.2 프론트매터

- 공통 필드 `title`, `type`, `created`, `updated`와 `status`, `sources` 필수.
- Workspace에서는 `target_folder: 05_Prototypes` 추가. 아래 예시는 Workspace용 설명 문서 형식.

```yaml
---
title: "프로토타입명"
type: prototype
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
status: draft
sources:
  - "[[01_References/문서명]]"
  - "[[02_Syntheses/문서명]]"
  - "[[03_Articles/문서명]]"
  - "[[04_Assets/리소스명]]"
target_folder: 05_Prototypes
---
```

- 확정 시 `reviewed`, `review_note` 추가. 정식 폴더 반영 시 `target_folder` 제거.

## 9.3 입력 근거와 검토 기록

- 입력 근거와 `sources`에 실제 사용한 `01_References`, `02_Syntheses`, `03_Articles`, `04_Assets`의 정식 문서와 리소스 기록.
- 재사용할 확정 리소스는 `04_Assets`에서 관리. 실행용 동봉 리소스는 프로젝트와 함께 보관하고 원본 출처 기록.
- 검토 결과와 한계에 실제 실행 여부, 핵심 동작, 입력 근거와 구현의 대응 관계, 실행 환경과 남은 한계 기록.
- 프로젝트 실행과 검증 결과는 해당 설명 문서에 기록. 확인하지 않은 항목은 미확인 상태로 명시하고 검증 완료로 기록 금지.
- 프로토타입의 실행과 검증 기록을 앞번호 지식 폴더의 근거로 사용하는 역방향 참조 불허.

# 10 System과 Logs

- System 문서는 공통 필드 4개와 실제 운영 내용 기록.
- 월별 로그는 `type: log`로 기록. 최신 내용의 삽입 절차는 [위키 작업 절차: 삽입과 정렬](위키%20작업%20절차.md#63-삽입과-정렬) 준수.
- 로그 한 항목의 기본 형식:

```markdown
# YYYY-MM-DD HH:mm: 작업명

- 대상: 변경한 문서 또는 파일 경로.
- 작업: 생성, 수정, 검증, 확정 등 실제 수행 내용.
- 이유: 작업 또는 변경의 근거.
- 검증: 실제 확인한 사항과 결과.
- 결과: 반영 위치, 현재 상태, 남은 작업.
```

- 시간은 별도 지정이 없는 경우 한국 표준시(Asia/Seoul)로 기록.

# 11 Workspace와 파일 이동

- Workspace 문서는 문서 종류에 맞는 프론트매터에 `target_folder` 추가.
- 정식 폴더 반영 시 `target_folder` 제거, 파일 경로와 링크 점검.
- 내용을 식별할 수 있는 제목과 파일명 작성. 기존 문서와 혼동되는 이름 사용 지양.
